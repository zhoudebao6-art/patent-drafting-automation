# 持续优化

用户可直接说“更新技能”“按这个问题优化规则”“用这份新定稿继续优化”。用户于2026-10-13明确：“你做的所有的技能更新都是通用更新不是一次性更新”。因此技能更新默认长期、通用、持久生效，以当前实际调用目录为准，先读取版本。

## 收集和分级

用户要求的技能更新记 user、scope=global，并在核查后设为active；后续所有适用项目和新批次默认加载，无需再次确认是否长期生效。只有用户明确说“仅本项目/仅本次”时才记project覆盖。基于案例提出的技能纠错须提炼成跨项目可执行的检查或写作规则，不能写成只匹配该案例名称的特判。未获用户要求通用化、仅自行观察到的案例差异仍先candidate；项目名称、技术参数、公式内容和实验数据始终留在各自来源，不能当作全局技术事实。

摘录改前/改后及来源，明确替换哪条约束；阅读旧规则做语义冲突审查。用户说“更新技能”即已授权长期通用化，不再追问是否仅本次，也不额外要求“加入技能/以后如此”字样；单纯要求改一段稿件而未要求更新技能时，仍只改该稿。

## 更新文件

patch 含 `expected_version` 当前版本、`summary` 实际用户意图、非空 `changes`。每项 action 为 add/replace/retire；add/replace 带完整 rule，replace 的 ID 已存在；retire 带 id。规则字段见 data-contracts.md。

例如用户明确要求长期优先保留可编辑公式，可加入 user 来源、global 范围的规则，evidence 定位到本次消息。若只要求项目甲如此，scope 必须是 `project:甲`。不要把维护文档里的示例视为已经发生的用户授权。

```text
python scripts/rules_tool.py apply --skill 当前技能目录 --patch 更新.json --dry-run
python scripts/rules_tool.py apply --skill 当前技能目录 --patch 更新.json
python scripts/rules_tool.py validate --skill 当前技能目录
```

脚本拒绝旧版本、重复 ID、缺证据或非法范围，备份旧库后原子写入并记历史；它不判断授权、语义矛盾或专业依据，应用前须审阅。失败时修复具体字段，不绕过版本检查覆盖。

## 验证和同步

按本次实际改动选择必要验证：规则语义变化核对适用/不适用情形；提取/缓存修改核对命中、失效、损坏证据和相关旧行为；仅涉及章节映射、所述父链、公式或删图联动时才重验对应项目。普通文案修改不跑全套批次测试。跨模块或关键验收契约改变时扩大回归，复杂更新用独立代理在临时目录执行代表性请求；通过后停止重复检查。

修改影响撰写规范或流程时同步相应参考文件，再验证，最后报告版本、变动规则、范围与检查结果。不能只修改 JSON 就声称所有文档完成更新。

工作区副本和安装版并存时，以实际加载路径为权威；比较版本和哈希，不用旧 ZIP 覆盖新安装版。回退通过新的版本变更恢复旧规则，保留既有历史，不直接回拨版本号。

不自动写用户长期记忆，不创建定时任务。后续增补通过再次调用此技能执行。

批处理配置变更同时同步batch-policy.json及batch-workflow.md；用户明确修改模型或交付配置时，还须同步parallel_batch.py中的对应校验及其测试，并保持batch_tool.py对旧批次的兼容，不能只改JSON导致执行被旧校验拒绝。修改普通话术不能顺带取消用户指定的Sol/high撰写、Astra/high复查及修正、每案阶段有序、跨案滚动并行及逐案验收后立即将成稿直接交付到桌面同一批次文件夹根目录。内部工作分区与最终交付布局分别维护，不能为了同层交付合并各案工作目录。已运行批次保留自己的策略快照；需要改变时先按用户明确要求迁移并记录，不能将新版本静默套用到半成品。
